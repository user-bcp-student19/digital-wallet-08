Presentamos cómo construimos un flujo multiagente con CrewAI que convierte un issue de GitHub Projects en diseño, backend, frontend, pruebas y una revisión final. La idea central: el LLM propone, las reglas validan (guardrails) y las personas deciden (human-in-the-loop).

¿Qué construimos?

Un equipo de agentes de IA que trabaja como un equipo de software: con roles, entregables y controles

VISIÓN

El reto

  • Un LLM genera rápido, pero puede inventar endpoints, romper la sintaxis o dar por bueno lo que nunca ejecutó.
  • Sin control, cada agente parte de supuestos distintos y el resultado no es trazable.

Nuestra respuesta

  • Orquestación determinista: main.py decide el orden y el contexto de cada agente.
  • Guardrails: reglas en Python validan cada salida y obligan al agente a corregirse.
  • Human-in-the-loop: las decisiones críticas las toma una persona.

Las cifras son las del main.py actual: Arquitecto, Backend, Frontend, QA y Chapter; cada uno con su guardrail; cinco decisiones humanas (elegir issue, aprobar Arquitecto, aprobar Backend, confirmar la ejecución de QA y aprobar sus resultados); y un único log que sale por consola y se guarda en output/ejecucion.log.

Cómo orquesta CrewAI

main.py es el director de orquesta: un Crew por agente, con contexto y reglas explícitas

ORQUESTACIÓN

↓

↓
Crew

↓
kickoff()

Process.sequential: cada paso espera al anterior. El contexto se inyecta como texto en la descripción de la tarea.

# main.py · execute(): un Crew por agente
crew = Crew(agents=[agent], tasks=[task],
            process=Process.sequential,
            verbose=False, stream=True)
streaming = crew.kickoff()
for chunk in streaming:        # texto en vivo
    print(chunk.content, end="", flush=True)
result = streaming.result
# make_task(): contexto + guardrail con reintentos
task = module.build_task(feature)
task.description += context
task.guardrail = _logged_guardrail(guardrail)
task.guardrail_max_retries = N
CrewAI · SDD · Billetera Digital5
En vez de dejar que CrewAI decida el orden, main.py ejecuta un Crew por agente. Así controlamos exactamente qué artefactos recibe cada uno, insertamos aprobaciones humanas entre pasos y registramos todo. La función make_task adjunta el guardrail y el número de reintentos; execute() usa stream=True para ver la respuesta en vivo.

Lo que hace distinto a este QA: separa quién diseña de quién mide

  • El agente solo diseña las pruebas; qa_runner.py levanta Backend y Frontend, ejecuta Karate y Selenium y mide.
  • El informe lo compila Python con la salida real de las herramientas: si algo no corrió, figura como NO EJECUTADO con su motivo.
  • Al terminar apaga los servicios y libera los puertos, incluso si algo falla.
CrewAI · SDD · Billetera Digital11
Un LLM no debería 'declarar' que las pruebas pasaron. Aquí el agente escribe las pruebas, pero quien las ejecuta y mide es código determinista (qa_runner.py). El informe testing.md sale de resultados reales. Verificamos este flujo de punta a punta con el Backend FastAPI y la app Angular reales: Karate y Selenium pasaron.

Las personas deciden en los puntos donde un error sale caro

HITL
1
Elegir proyecto e issuePor número, con validación de entrada
2
Aprobar el Arquitecto[s] aprobar · [r] reintentar con feedback · [n] abortar — sin límite de intentos
3
Aprobar el Backend[s] [r] [n] — máximo 3 intentos; después se cierra el ciclo
4

5
Aprobar resultados de QA[s] aprobar · [r] regenerar pruebas · [x] reejecutar · [n] abortar

Todas las respuestas se registran en el log: quién decidió qué y cuándo.

CrewAI · SDD · Billetera Digital14
El humano no revisa código línea por línea: ve la salida ya validada por el guardrail y decide. Si elige 'r' da feedback en texto libre y el agente lo recibe como corrección. En el Arquitecto no hay límite porque es la especificación; en el Backend hay máximo de tres intentos. QA tiene dos pausas: antes de ejecutar (porque se instalan dependencias y se ejecuta código generado) y antes de publicar reportes.

Control de riesgos incorporado

Un agente que ejecuta código necesita límites claros

SEGURIDAD
🔑

Sin secretos

Guardrails rechazan tokens y claves; el entorno de ejecución filtra variables TOKEN, SECRET, COPILOT…

📁

Rutas seguras

Los archivos generados no pueden salir de su carpeta (sin '..', sin rutas absolutas)

🚫

Código prohibido

eval, exec, subprocess, pickle, innerHTML y bypassSecurityTrust* se rechazan

🙋

Ejecución con permiso

Instalar dependencias y levantar servicios requiere tu confirmación explícita

🧹

Limpieza controlada

Solo se detienen procesos propios del pipeline; nunca procesos ajenos

📋

Honestidad de resultados

Lo que no se ejecutó se informa como NO EJECUTADO, no se inventa

CrewAI · SDD · Billetera Digital17
Seis controles que aplicamos. Los guardrails bloquean contenido peligroso; los procesos generados se ejecutan con un entorno sin credenciales y solo tras confirmación humana; los archivos se escriben bajo rutas validadas; y el informe nunca afirma lo que no se ejecutó.
